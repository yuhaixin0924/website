### Malloc Lab

Malloc Lab 的任务，是实现 `mm_malloc`、`mm_realloc`、`mm_free`，以及一系列配套的辅助函数。

我使用的是隐式空闲链表。每个块的大小和分配状态保存在 header 和 footer 中。它的缺点也很明显，查找空闲块时需要顺着整个堆逐块遍历，效率不高。我最后也没有继续实现显式空闲链表。

不过现在回头看，我觉得这个 Lab 最有意思的地方并不是最终采用了哪种链表，而是几个函数之间如何互相配合，并共同维护堆的状态。

#### 几个函数如何串起来

堆初始化以后，内存中并不是什么都没有。开头和结尾会设置序言块与结尾块。它们更像是两个哨兵，可以让边界判断和块合并的逻辑保持统一。

`mm_malloc` 的原则很简单，能复用已有空闲块，就先不扩展堆。因此它首先调用 `find_fit`，寻找一个足以容纳当前请求的空闲块。

找到空闲块以后，还不能直接把整块空间全部交出去。`place` 需要判断剩余空间是否足以形成一个合法的新块。如果可以，就把原来的空闲块切成已分配部分和剩余空闲部分，从而减少内部碎片。

如果 `find_fit` 没有找到合适的块，`mm_malloc` 才会扩展堆，再从新获得的空间中完成分配。

我当时想过一个问题，为什么不等到 `mm_malloc` 查找空间时，再检查相邻空闲块能不能合并？

后来发现，这样做会让每次分配都承担额外的合并检查。相比之下，`mm_free` 已经知道刚刚被释放的块在哪里，所以更适合在这个时机调用 `coalesce`，有针对性地检查前后相邻块。

这样一来，所有由 `mm_free` 产生的相邻空闲块都会尽早合并。等到 `mm_malloc` 再次遍历堆时，看到的已经是合并后的结果。这种设计把不同职责放在了更合适的位置。

`mm_realloc` 也借用了一部分这种思路。为了尽量保持返回地址不变，我的实现只尝试向右检查相邻空闲块。如果右边有足够空间，就直接扩展当前块。这个实现并不完整，但逻辑比较直接。

Malloc Lab 留给我的一个印象是，内存分配器并不是简单地寻找一块空地。它真正做的是维护一组必须始终成立的结构约束。一个 header 写错、一处块大小计算错误，可能不会立刻出问题，却会在之后的某次分配或释放中破坏整个堆。

### Proxy Lab

Proxy Lab 让我第一次比较完整地把网络、线程、文件描述符和缓存放进同一个程序里。

它和 Shell Lab、Cache Lab 有一些相似之处。程序需要先划分职责，再考虑并发情况下怎样维护共享状态。

在我的实现中，主线程只负责监听端口和接受新连接。每当有客户端连接，`Accept` 会返回一个新的 `clientfd`，主线程再创建一个工作线程处理它。

```cpp
listenfd = Open_listenfd(argv[1]);
    while(1){
        clientlen =sizeof(clientaddr);
        int * clientfd_ptr =Malloc(sizeof(int));
        *clientfd_ptr=Accept(listenfd,(SA *)&clientaddr,&clientlen);
        Pthread_create(&tid,NULL,thread,clientfd_ptr);
    }
```
这里有一个我一开始没有想清楚的问题。
pthread_create 的第四个参数是一个 void *。如果把循环中反复使用的局部变量地址直接交给工作线程，主线程可能在工作线程读取之前就修改了这个变量。最后，两个线程可能拿到同一个已经更新过的 clientfd。
因此，我为每次连接单独申请一块内存，把 Accept 返回的 fd 存进去，再把这个地址传给线程。工作线程取出 fd 之后，需要释放的是保存 fd 的临时内存：
```cpp
int clientfd = *(int *)arg;
Free(arg);
```
这里释放的不是网络连接。真正关闭连接需要调用 Close(clientfd)。
工作线程随后调用 doit，完成一次请求的主要流程：
```
读取并解析客户端请求
解析目标主机、端口和路径
连接目标服务器
重新组织 HTTP 请求
把请求转发给服务器
读取服务器响应
把响应转发给客户端
```
### Shell Lab
Shell Lab 是我第一次真正感觉自己在和操作系统打交道。
现在回头看，我对其中一些细节已经有些模糊。进程、信号、前后台任务和竞态条件，我大概知道它们分别在解决什么问题，但还没有形成足够稳定的整体理解。
所以这部分暂时不打算强行总结。我准备等做完 CS61C 的 CPU Project，再回头重新看一次 Shell Lab。也许到那个时候，我会对程序、进程、线程、CPU 和操作系统之间的关系有新的理解。
### 关于 AI 和编程
写 Proxy Lab 的过程中，我有一段时间挺挫败的。
AI 可以很快生成一个完整的缓存结构，也可以直接给出 cache_send、cache_insert 和 LRU 淘汰的实现。相比之下，我可能连一个函数为什么要传指针都需要反复追问。
我后来开始怀疑，AI 时代还有没有必要要求自己从空白写出这样的程序。
现在的想法是，我没有必要和 AI 比拼生成代码的速度。但我至少应该知道代码在维护什么、依赖什么，以及怎样判断它是否正确。
技术我觉得可以慢慢积累，可能我是一个学习速度一般，有点lazy的人，总之不强求自己一次性就能够又快又好地完成很多，只要有一个可以长期坚持下去的条件（身体and心态）,最后的结果虽然不是第一，但也不会差到哪里去。当然啦，我现在还是改不了焦虑和内耗的习惯，但是做一个普通的，心态普通的人，又有什么错呢hhh
